# Study notes — Gateway API Inference Extension, state as of 2026-07-11

Targeted study for ADR-0006 (disaggregation-aware orchestration).
All facts verified against official kubernetes-sigs / llm-d repos and docs
on 2026-07-11. The project moves fast: treat these notes as dated evidence,
not as a living reference.

## Project status and versions

- Gateway API Inference Extension (GIE) is GA. Current release: **v1.5.0**
  (2026-04-19).
- **InferencePool is graduated to v1, stable**: API group
  `inference.networking.k8s.io/v1`.
- Repository restructuring (kubernetes-sigs issue #2430): the EPP,
  InferenceObjective, InferenceModelRewrite and BBR packages moved out of
  `kubernetes-sigs/gateway-api-inference-extension`. That repo now hosts only
  the lightweight EPP (LWEPP), the InferencePool API, and conformance tests.
  The EPP and associated APIs live in **`llm-d/llm-d-router`** (formerly
  llm-d-inference-scheduler). Community meetings moved to the llm-d Router
  meeting.
- llm-d was donated to CNCF on 2026-03-24 (Sandbox).
- `InferenceModel` is gone. Replaced by **InferenceObjective** (per-request
  priority, attached to an InferencePool, selected via the
  `x-gateway-inference-objective` header) plus `InferenceModelRewrite`.
- Practical reading: "build on Gateway API Inference Extension" today means
  *InferencePool v1 as the contract + the llm-d-router EPP as the scheduler*.

## InferencePool v1 primitives

- Spec has three main parts: `selector` (must exactly match model-server pod
  labels), `targetPorts`, and `extensionRef` (the Endpoint Picker service,
  with `failureMode`, e.g. FailOpen).
- It is a Gateway API backend: HTTPRoute `backendRefs` points to
  `kind: InferencePool` instead of a Service.
- Cardinality: one EPP serves exactly one InferencePool. Current llm-d
  assumption: single InferencePool + single EPP (Envoy limitations), one base
  model per pool (multiple models = multiple pools).

## How disaggregation actually works (llm-d-router)

Key architectural fact: **no separate pools per role**. Prefill and decode
pods live in the *same* InferencePool; role separation is done by the EPP via
pod labels and scheduling profiles.

- **Label convention**: key `llm-d.ai/role`, values `prefill`, `decode`,
  `encode`, `prefill-decode`, etc. Alternative conventions supported without
  code changes via the generic `label-selector-filter` plugin (`by-label` is
  deprecated).
- **EPP configuration**: `EndpointPickerConfig` (`llm-d.ai/v1alpha1`,
  file or inline), with `plugins` + `schedulingProfiles`. Disaggregated
  prefill requires two profiles (one filtering prefill pods, one decode pods,
  each with `prefix-cache-scorer` + `max-score-picker`).
- **P/D decision flow**: the `disagg-profile-handler` always selects the
  decode pod first; then the `prefix-based-pd-decider` checks how many prompt
  tokens are already cached on that pod. If the non-cached suffix exceeds
  `nonCachedTokens`, disaggregation triggers and a prefill pod is selected;
  otherwise the whole request runs locally on the decoder. Disaggregation is
  therefore **per-request and cache-driven**, not static.
- **Data plane**: the selected prefiller travels in the
  `x-prefiller-host-port` header; a sidecar on the decode worker only
  orchestrates the remote prefill (max_tokens=1), receives remote KV
  parameters, and the decoder reads the KV cache from the prefiller. No
  sidecar on prefill/encode nodes.
- **Scorers**: `prefix-cache-scorer` (approximate per-server LRU:
  `blockSizeTokens`, `lruCapacityPerServer`) or
  `precise-prefix-cache-producer` (KV events). Worker selection: longest
  prefix match + low load, same criteria for prefill and decode.
- **Limitations stated by the project itself**: TTFT increase, possibility of
  stranded memory on prefiller crash, need for timeout/retry logic. This
  independently confirms the vllm-disagg-profiling findings (prefiller power
  ratio 3.66x at decode-heavy load, TTFT +278ms at prefill-heavy load).
- Encode disaggregation (E/PD, E/P/D): PoC under active development in both
  vLLM and llm-d-router, subject to change. Out of scope for ADR-0006.
- GIE roadmap: "Disaggregated serving support with independently scaling
  pools" is still roadmap, and IGW states the intent to generalize the llm-d
  disaggregation plugins into a cross-model-server standard. The multi-pool
  standard **does not exist yet**: building today means building on
  single-pool + role labels.

## Integration points for vllm-coldstart-operator

1. **Clean division of responsibility**: EPP = per-request scheduling
   (already cache-aware, already written). Operator = what the EPP does not
   cover: pod lifecycle, warmth, placement, per-role recovery. Zero overlap:
   the operator complements llm-d rather than competing with it.
2. **Minimal integration contract**: the operator labels pods with
   `llm-d.ai/role` and guarantees the InferencePool `selector` includes them.
   Open decision: operator *owns* the InferencePool (creates it as a child
   resource) or only *references* it.
3. **Asymmetric warmth (the core of the ADR)**: decoder warmth has two
   levels (model-loaded + cache-content); the EPP tracks per-endpoint prefix
   state, so replacing a decode pod resets its score and the router penalizes
   it until it re-warms. The prefiller is stateless between requests (KV is
   transferred via the header flow): aggressive recovery is fine, with a
   guard against stranded memory. The current validated make-before-break
   (57s replacement) must be **differentiated per role**.
4. **The energy-to-orchestration bridge is quantified**: the decider
   disaggregates as a function of prefix hit rate; a placement/recovery
   policy that destroys cache content shifts the workload regime from H2
   toward H0, a measured cost of up to **-69.2% tok/J** (18/18 confirmation
   matrix, H100, agentic-kv-energy-experiment). This is the number that
   motivates the ADR.

## ADR-0006 decision outline (draft)

- **D1 — Resource model**: (A) new dedicated CRD vs (B) extend
  `FleetService` with a `roles:` field (map role -> replicas / resources /
  warmth policy). Leaning B: the P/D graph is a refinement of the validated
  fleet model, reusing existing CRDs and reconcilers.
- **D2 — GIE alignment**: adopt InferencePool v1 as the contract (selector +
  `llm-d.ai/role`); do not invent a parallel pool concept. Sub-decision: own
  vs reference the InferencePool. Leaning reference-by-default with optional
  ownership, to avoid conflicts with existing llm-d Helm deployments.
- **D3 — Per-role warmth semantics**: decode = `ModelLoaded` + `CacheWarm`
  (signal: `vllm:prefix_cache_*` metrics, already covered by inferscope
  `is-metrics`); prefill = `ModelLoaded` only.
- **D4 — Differentiated placement/recovery**: decode = warm spare +
  cache-aware drain-and-hold, with lost-cache cost as a first-class metric;
  prefill = fast replace + stranded-memory guard. Extends the existing
  make-before-break rather than replacing it.
- **D5 — Scope**: P/D only; E/P/D explicitly out of scope (upstream PoC).
